# ADR-0045 — Декларациите се обработват в контейнер в Cloudflare; публикуването е размяна на таблици

- **Статус:** Прието
- **Дата:** 2026-09-17
- **Обхват:** `apps/etl` (Durable Object `DeclarationContainer`, Workflow `sigma-declarations`,
  `containers/declarations`), `scripts/ship-related-persons.mjs`, `.github/workflows/deploy.yml`.
  Заменя рамката „седмично задание в GitHub Actions“ на [ADR-0034](0034-registry-lookups-and-decisions-share-one-monthly-run.md)
  и предложението на [ADR-0038](0038-reseed-writes-idle-slot-gates-read-live.md).

## Контекст

Заданието за свързаните лица беше единственият процес, който пишеше данни в D1 отвън: седмичен
workflow в GitHub Actions теглеше регистъра на декларациите, смяташе връзките и ги публикуваше с
токен на изпълнителя. Всичко останало (поръчките, регистърът) вече върви в Cloudflare. Контейнерът,
който изпълнява същия скрипт под Durable Object с R2 за корпуса, беше написан, проверен на dev и
оставен зад флаг.

Публикуването в D1 сравняваше качените междинни таблици с обслужваните и прилагаше разликите в
една заявка с trigger. Сливане на лица ([ADR-0042](0042-declarant-identifier-as-identity-evidence.md))
мести всички документи между лицата и разменя вторичните им уникални ключове; такава разлика
надхвърля процесорния лимит на D1 за една заявка и не минава.

## Решение

1. **Само Cloudflare пише в Cloudflare.** Седмичният cron на etl worker-а стартира хода на
   декларациите в контейнера; шестчасовият cron остава за поръчките и регистъра. Workflow
   `sigma-declarations` е операторският спусък за същия ход и приключва с реалния му резултат.
   GitHub деплойва кода и подава на worker-а секретите, с които контейнерът публикува.
   Workflow-ът в GitHub Actions за данните и кешът му на корпуса отпадат; корпусът живее в R2.
2. **Публикуването е размяна на таблици.** Междинните таблици носят схемата на обслужваните, с
   външни ключове към междинните си родители. Една атомарна партида прави обслужваните таблици
   `rp_prev_*`, а междинните вземат имената и индексите им. Партидата не пише редове, затова обемът
   на промяната е без значение; грешен ред отпада при качването, преди да е докоснал обслужван
   ред; предишното поколение стои до следващата публикация и връщането назад е същата размяна
   обратно.

## Последствия

- Проверено на D1: файл с няколко заявки се изпълнява като една транзакция, а външните ключове и
  индексите следват `ALTER TABLE … RENAME`.
- Слотовете blue/green остават за пълното презасяване на поръчките. Свързаните лица вече не се
  нуждаят от тях за дълбочина на връщане назад, затова разделянето по ADR-0038 не се прилага.
  Пълно изграждане на неактивния слот от всички процеси и превключване е отделно бъдещо решение.
- Обхватът на контейнера е един ход наведнъж; Durable Object-ът връща текущия ход при повторно
  стартиране.
